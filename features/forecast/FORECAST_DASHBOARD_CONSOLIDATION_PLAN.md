# CRM Forecast and Teams Dashboard consolidation

**Date** 20 November 2026  
**Status** Proposed implementation plan. Deployment pending.  
**Scope** Crusource CRM frontend and backend. Source baseline at frontend `f1f76a5a` and backend `ff60d65`. Findings are from local source inspection. Tenant configuration, saved content counts, and deployed behavior require separate verification.

## Product decision

Choose **Option 1**. Give every eligible CRM user a personal **My Sales Target & Forecast** section on Home. Put cross-user forecasts, quota assignment, and team goals in **TeamSpace → Teams Dashboard**. Keep the Standard profile’s existing default of Teams Dashboard disabled. Move Teams Dashboard configuration into **Profiles & Permissions → TeamSpace** and keep **Admin Hub → Pipelines & Stages** as the stage probability editor.

| Surface | User workflow |
| --- | --- |
| Home | See your month or quarter quota, closed-won revenue, weighted open pipeline, attainment, and deals that need close-date attention. Open an eligible deal directly from the widget. |
| Teams Dashboard | Review authorized team or reporting-branch performance, inspect eligible deals, and assign sales quotas or activity goals if authorized. |
| Reports and Analytics | Build, run, and export authorized Forecast reports. Existing reports and board widgets retain their IDs and definitions. |
| Profiles & Permissions → TeamSpace | Configure Teams Dashboard access and scoped target/goal permissions alongside existing TeamSpace settings. |
| Admin Hub → Pipelines & Stages | Configure probability on editable pipeline stages. |

Option 2 would make the dashboard serve two different jobs and require conditional behavior on every team panel. Home serves the rep’s daily workflow and leaves room to add individually assigned activity goals later through a self-only read. Keep the first Home release focused on personal sales quota and pipeline. Treat quota figures and pacing as private CRM data.

Consolidate the **management workflow** in this release. Keep the two existing data models because calendar-period revenue quotas and custom-period goals have different semantics. Retire the standalone Forecast navigation and its module entry after authorization and report compatibility are in place. Retain the Forecast calculation service and report entity.

## Authorization contract

Treat dashboard access, subject visibility, record visibility, field visibility, and write permission as separate checks. Tenant ID always comes from the authenticated session. Derive capabilities from the effective profile, including role-profile inheritance. A top RoleNode, a legacy manager label, a client route, and ordinary membership each have their own semantics. Organization-wide performance access requires effective administrator authority. Delegated organization-wide performance for custom profiles would require an explicit future product decision.

| Audience | Home | Team performance | Assignment |
| --- | --- | --- | --- |
| Standard with normal Deals access | Owned, readable deals and own authorized quota | Disabled by default | Denied |
| Effective team leader with Teams Dashboard enabled | Same personal scope as any user | Reporting descendants and eligible members of explicitly managed teams, with module and field restrictions | Separate action grants within management scope |
| Custom leader with dashboard access and no write grants | Own data | Authorized team data only | Denied |
| Leader with Teams Dashboard disabled | Own data | Denied on direct navigation, API calls, and dashboard export | Denied through Teams Dashboard |
| Organization Administrator | Own data | Authorized organization data with optional filters | Within the same organization |
| Reports user | As above | Dashboard access follows TeamSpace permissions | Forecast reporting follows its own scoped grant, report access, and source permissions |

### Resolve scope before computing metrics

1. **Home** derives the subject from `scope.user_id`. Accept period, eligible pipeline, and currency only. Personal ownership still requires valid record access and readable fields. Deny or omit metrics for disabled Deals access. Preserve previous explicit Forecast denials for personal quota visibility until the profile is reconfigured. Use the same self-only contract for any later individual activity goals.
2. **Team performance** requires `teams_dashboard` plus effective leadership or organization admin. Reuse the active, organization-scoped `User.reports_to` traversal for direct and skip-level reports. Include eligible members of an active team the viewer explicitly manages, using existing hierarchy authority to exclude the viewer's superiors and protected users. A same-team peer in an unmanaged team sits outside scope. Evaluate role-node restrictions where they apply to branch authority. Role-node rank alone never identifies a person's reporting manager. Keep the caller's own performance on Home and exclude it from a non-admin team rollup. Preserve a valid explicit self-assignment only if that authority is approved during migration review. [Reporting traversal](../../../crusource-crm-backend/src/shared/auth/reporting_tree.py), [branch authority](../../../crusource-crm-backend/src/modules/admin/services/hierarchy_permission_guard.py)
3. **Filters narrow the result.** An explicit team must be authorized and active. For team-affiliated deal and activity rows use stored `record_team_id` under existing record policy plus the authorized subject filter. A quota follows its assignee and period. For a selected team, use current authorized membership to select its quotas and label the team forecast as based on current assignments. For branch-wide results, count each user and quota once, including eligible reports without team membership. If selected-team membership differs from deal affiliation, expose that difference clearly or omit the corresponding attainment ratio pending a defined comparable population. Keep org and unassigned scopes explicit, with unassigned restricted to organization admins. A disallowed team or user returns a consistent access error, never an unfiltered fallback.
4. **Use the record policy for source data.** Intersect the subject set with module access, applicable TeamSpace record policy, effective owner/assignee rules, and field permissions before calculating totals or building row payloads. An explicit record share or collaboration role may allow operational access while leaving the owner outside the performance cohort. Reuse the scoped query helpers where their semantics fit. Keep pool visibility and approvals independent. Apply scoping to dropdowns, names/counts, hierarchy trees, goal progress, feed, errors, pagination totals, exports, and all drilldowns. Omitting a hidden financial field from the response still leaves leakage through a percentage, filter, total, or notification.
5. **Authorize writes independently.** Require active subscription for mutations where applicable, the relevant action grant, organization membership, and assignment authority on the persisted object or proposed assignee. Require full authorized coverage before assigning a team-wide goal. For a partially visible team, suppress whole-team goal progress, including the denominator. Apply ordinary deal update, field-level write, and approval rules to close-date actions. Recheck authority in the handler for legacy routes, CSV exports, and internal callers that can bypass route dependencies.

The trust boundaries are the browser to CRM API, the reporting and export consumers to source data, and the scheduler to notification delivery. The same tenant, subject, and field checks apply on each boundary.

| Risk | Required control |
| --- | --- |
| Cross-branch financial disclosure through filters, aggregate counts, exports, cached reports, or notification history | Apply effective scope before queries and aggregation. Invalidate client data on authorization changes and recheck sensitive server reads. |
| Privilege escalation through a legacy route or permission backfill | Apply equivalent guards to all entry points. Preserve explicit denies and action-specific grants. Audit assignment and profile changes. |
| Expensive reporting or drilldown requests degrade Home or Teams Dashboard | Require bounded periods and pagination, reuse existing request controls, and verify query plans and request counts using representative data. |

## Implementation sequence

### 1. Patch authorization before moving screens

**Backend first.** Introduce a reusable performance scope around existing auth, reporting-tree, and record primitives. Pass explicitly resolved subjects and record authorization into the Forecast repository, summary, drilldown, and target queries. Use the same filtered input for aggregate and drilldown. Stabilize the existing Forecast API in place during this phase. Preserve existing Forecast grants as upper bounds. Retain deal-action governance in the existing close-date command and constrain the new Home flow to owned deals. [Forecast repository](../../../crusource-crm-backend/src/modules/forecast/repositories/forecast_repository.py), [close-date command](../../../crusource-crm-backend/src/modules/forecast/handlers/bulk_update_close_date_handler.py)

Add the Teams Dashboard guard to stats, comparison, dashboard CSV, dashboard roster/hierarchy, and any dashboard-only feed or goal endpoints. Preserve shared routes used by operational flows with purpose-specific data and policies. Require a scoped goal grant on definition and progress reads and action grants on writes. Protect legacy routes while clients transition. Compare and export from the same scoped inputs as the screen. Keep coaching-note and feed call sites in the inventory and enforce their own privacy controls wherever surfaced in the dashboard. [CSV routes](../../../crusource-crm-backend/src/modules/teamspace/routes/teamspace_export_routes.py), [dashboard and collaboration routes](../../../crusource-crm-backend/src/modules/teamspace/routes/teamspace_collaboration_routes.py)

Apply the standard pipeline lock to the legacy Forecast probability writer in this phase. Verify editable pipelines still work until the alternate write path is retired.

Patch notification delivery in this phase. Achievement goes to the eligible assignee. Manager delivery goes to authorized recipients resolved from the subject’s current reporting relationship and effective target visibility. Default to the eligible direct supervisor for manager alerts. An authorized administrator can inspect team performance on the dashboard. For any historical notification containing restricted financial detail, assess existing rows through an approved read-only inventory. Suppress or redact unauthorized display server-side, including specialized reads or push payloads, and avoid destructive cleanup in this release. Store only the detail needed for the alert. Check eligibility at send time and when rendering sensitive history.

**Exit criteria** Scope regression tests cover legacy APIs, dashboards, reports, exports, notifications, and shared assignee workflows. Direct access to team data obeys the same constraints as the UI. Deploy this slice independently when it passes the appropriate release checks.

Keep the five per-module TeamSpace policy editors. Reuse the normal profile save path, effective-permission endpoint, template and clone handling, existing inheritance, and audit history. Gate the dashboard route and queries with the same resolved capability.

Add explicit **View team forecast and quotas**, **View team goals**, and independent action permissions for sales targets and team goals. Match available operations initially: quota create/edit/delete and goal create/delete. An optional single label in the editor can summarize actions while preserving each saved grant. Require Dashboard and view access as prerequisites for writes. Place Forecast reporting access under Reports, independently of Teams Dashboard. Use an additive, idempotent permission backfill with tests on legacy and current profiles. Preserve explicit denies. For existing profiles, cap team forecast grants by the intersection of prior Forecast view, current leadership, Teams Dashboard access, and the stricter hierarchy policy. Carry each granted quota action independently. A Manager seed currently grants Forecast create/edit and denies delete, which the migration must preserve. Historical Team Goal access depended partly on role labels, so start custom profile goal writes denied unless the mapping has been reviewed and approved. Default Standard to dashboard disabled and personal access consistent with its current own grant. Carry existing Forecast report scope and quota field access to a report-specific capability, intersected at runtime with report access, Deals access, strict subject scope, and source field policy. Stop using legacy Forecast as an input to leadership eligibility only after checking profiles and templates where it was the sole qualifying grant. Keep audit entries readable.

Use a compatibility window with dual-read logic that resolves new permissions first and falls back to the equivalent tightened legacy decision only for unmigrated records. Make explicit denial win over fallback. Reuse existing permission invalidation and protect cache reuse after profile, role, team, or organization changes. If reverting to an older frontend, keep the API enforcing the tighter policy.

| Proposed contract | Purpose and minimum payload |
| --- | --- |

Use the existing CQRS and router-registration conventions for these contracts. Return access failures consistently, distinguish empty scope from no quota, and keep optional financial values nullable. Validate period, currency, bucket, and pipeline centrally. Return only fields each consumer needs.

## Data preservation and rollout

- Inventory existing profile and template scopes, active memberships, managed teams, missing reporting links, Forecast reports, Analytics report references, goal types, currency mixes, and legacy notification types using approved read-only access. Record aggregate counts and compatibility exceptions without recording private financial values. Use representative fixtures if access is pending and keep real tenant verification open.
- Sequence changes across repositories as **tightened compatible backend → additive permission migration and contracts → frontend adoption → compatibility observation → retirement**. Backend and frontend must work under old-frontend/new-backend overlap. Land permission changes before requiring them. Keep mutations single-path through shared handlers so data written during rollout remains readable after rollback.
- Prefer reverting only the frontend cutover or disabling the new views with an existing authorized rollout mechanism if available. Keep the authorization and notification fixes active. If backend rollback is required, roll back to the hardened compatible backend and keep additive permission data and business rows. Freeze retirement if any authorized saved report, widget, or shared TeamSpace flow still depends on a legacy contract.
- Compare target and goal row counts and IDs, profile grants, stage probability values, saved report IDs, widget bindings, and notification behavior before and after migration. Surface meaningful scope and currency differences during validation.
- If a single table becomes a product requirement later, design it after the workflow ships. Specify target kind, subject type, cadence, canonical period or range, currency, uniqueness, and origin IDs. Backfill transactionally with repeatable conflict reporting and reconcile amount, note, ownership, audit, and notification references before any cutover.
